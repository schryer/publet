# Conformance

The Gherkin suite is the conformance definition. It is not a description of
this implementation: it drives binaries as a user would, resolves them from
one environment variable, and asserts on exit codes and bytes. An
implementation in any language can run it unmodified.

## Running it against another implementation

Build binaries matching the plumbing interface, put them in one directory,
and point the suite at it:

```sh
export PUBLET_BIN_DIR=/path/to/your/binaries
pytest tests/ -m conformance
```

`-m conformance` selects the scenarios that exercise a normative statement.
Dropping it runs everything, including scenarios about this implementation's
own conveniences, which another implementation is not obliged to share.

The binaries the conformance scenarios invoke:

| Command | Reads | Writes |
|---|---|---|
| `pub-canon` | object bytes on stdin | the same bytes, or exit 1 naming the violated rule |
| `pub-cid` | object bytes on stdin | the identifier |
| `pub-verify` | object bytes, `--cid=` | confirmation, or exit 1 |
| `pub-sign` | object bytes, `--purpose=`, `--message` | the domain-separated signing message, hex |
| `pub-ls` | `--dir=` | identifiers, one per line |
| `pub-lineage` | `--dir=`, a CID | lineage members, one per line |
| `pub-divergence` | `--dir=`, two CIDs | JSON lines naming divergent and stale terms |
| `pub-merkle` | identifiers on stdin | the membership root |
| `pub-proof` | identifiers on stdin, `--member=` | JSON naming present or absent |
| `pub-delta` | `--dir=`, `--from=`, `--member=` | JSON, or exit 1 on a malformed record |
| `pub-eval` | `--vector=` | a standing as one JSON line |

Exit codes are uniform: `0` success, `1` protocol violation, `2` usage,
`3` not found, `4` I/O.

## Vectors

`vectors/` holds byte-level cases that do not depend on any implementation:

| Directory | Contents |
|---|---|
| `canonical/` | one file per rejection rule, plus accepted forms. `REJECTIONS.txt` names the rule each must report. |
| `cid/` | byte strings and the identifiers they must produce, in `EXPECTED.tsv`. Cross-checked against `sha256sum`. |
| `signature/` | a target object and the signing message each purpose must produce, in `MESSAGES.tsv`. |
| `eval/` | evaluation inputs with policies and evidence. Output must be byte-identical across implementations and architectures. |
| `invalid/` | inputs that must be refused. |

The vectors were generated by the Python suite, not by this implementation.
A vector the code under test produced could show only that the code is
self-consistent.

## Coverage

`COVERAGE.md` maps every section of the specification containing normative
language to the scenarios exercising it, and lists the sections with none.
Regenerate it with:

```sh
./tools/must-coverage.py --report=conformance/COVERAGE.md
```

The gaps are published rather than hidden. A report showing only what passes
would say nothing about what is untested.

## Proving the suite can fail

A suite never shown to fail is not evidence of anything. `verify-suite.sh`
breaks one specification rule at a time, rebuilds, and asserts the suite
notices:

```sh
./conformance/verify-suite.sh
```

It currently breaks canonical-form rejection, the replication floor, and
the requirement that a removal carry a justification. Each is reverted
afterwards. When a case goes undetected that is a gap in the suite, not in
the implementation -- which is how the generation scenarios were found to be
placeholders rather than tests.
